portal-monitor

Portal Safe Browsing Monitor

调用 Google Web Risk Lookup API，检查配置的域名或 URL 是否在威胁列表中。 只有有效安全状态变化时，才通过 Teams Webhook 通知。Production 跑在 EKS CronJob 上， 按北京时间每 6 小时一次（每天 4 轮）。

Overview 1. Local 2. Docker 3. Kubernetes 4. CI / CD 排障

Overview

这个仓库解决什么问题

对每个域名 / URL 调一次 webrisk.googleapis.com/v1/uris:search， 用返回的威胁列表命中结果和 status.json 里上次结果对比。

  1. 1

    调 Lookup API

    每个条目一次 HTTP GET，带 API Key 和要查的威胁类型。

  2. 2

    解析成三种状态

    SAFE / UNSAFE / CHECK_ERROR

  3. 3

    和 status.json 比较

    只有 SAFE ↔ UNSAFE 变化（含首次 UNSAFE）才发 Webhook。

  4. 4

    通知 Microsoft Teams

    经 Power Automate Workflow 触发器投递到频道。

适合盯一组业务域名或具体 path。状态没变不刷屏； CHECK_ERROR 不会覆盖已经落盘的有效 SAFE / UNSAFE。

Lookup API 是 URL 级匹配，不是整站判定。 Web Risk 会对传入 URI 展开若干 host 后缀与 path 前缀组合再比对， 所以整个域名被列入名单时查任意路径都会命中； 但只有某个具体页面被标记时，查首页不会命中。

需要盯特定路径时，在 domains.txt 里直接写完整 URL。

一次运行做了什么

入口是 app/monitor.py，只依赖 Python 标准库，requirements.txt 是空的。

  1. 校验 WEBRISK_API_KEY 和 THREAT_TYPES，缺失直接以 2 退出。
  2. 读域名列表（本机 domains.txt；K8s 挂 ConfigMap 到 /app/domains.txt）。跳过空行和 #，去重并保序。
  3. 读状态文件（本机 status.json；容器 /data/status.json）。不存在则视为空。
  4. 逐个条目补全 URI（裸域名加 https://），GET uris:search。
  5. 异常最多重试 3 次（MAX_RETRIES），间隔 RETRY_DELAY_SECONDS。
  6. 决定是否覆盖状态、是否加入通知队列。
  7. 先写 status.json.tmp 再原子替换，避免写一半损坏。
  8. 对每个 status_changed 事件 POST 到 ALERT_WEBHOOK_URL。

请求形如：

GET https://webrisk.googleapis.com/v1/uris:search
      ?uri=https%3A%2F%2Fportal.boruxa.com
      &threatTypes=MALWARE
      &threatTypes=SOCIAL_ENGINEERING
      &threatTypes=UNWANTED_SOFTWARE
      &key=API_KEY

检查是串行的，但一个条目只是一次 HTTP 调用， 百来个域名也在一分钟内跑完。activeDeadlineSeconds 为 600。

CronJob 使用 concurrencyPolicy: Forbid：上一轮没结束，下一轮自动触发会被跳过。6 小时的间隔下不可能重叠。

Status

状态 含义 判定依据
UNSAFE 该 URI 命中至少一个威胁列表 响应里 threat.threatTypes 非空。 命中的类型只写进日志，不进 Webhook 负载。
SAFE 该 URI 不在任何被查询的威胁列表中 响应是空对象 {}。 注意这是「未命中」，不等于 Google 主动背书该站安全。
CHECK_ERROR API 调用异常，重试耗尽 超时、429、5xx。 运行异常，不是 Google 给出的安全结论。

默认查询三个威胁列表，可用 THREAT_TYPES 覆盖：

MALWARE
SOCIAL_ENGINEERING
UNWANTED_SOFTWARE

命中时的响应：

{
  "threat": {
    "threatTypes": ["MALWARE"],
    "expireTime": "2026-09-18T15:01:23.045123456Z"
  }
}

400 / 401 / 403 表示 API Key 无效或 Web Risk API 未启用。 重试无意义，且剩余域名会以同样方式失败，所以立即中止整轮并以 2 退出， 而不是把整份清单打一遍再报一堆 CHECK_ERROR。

官方测试 URL testsafebrowsing.appspot.com/s/malware.html 可以用来确认 Key 真的能拿到命中结果。

Alert Logic

会通知

  • 第一次有效检查就是 UNSAFE
  • 已有状态在 SAFE ↔ UNSAFE 之间切换

Payload：event: status_changed，含 domain / previous / current / time。

不通知

  • SAFE → SAFE、UNSAFE → UNSAFE
  • 第一次是 SAFE（只落盘）
  • CHECK_ERROR
  • 未配置 Webhook（仍检查、仍写状态）

遇到 CHECK_ERROR 时，若该域名已有上次 SAFE / UNSAFE，会保留旧值， 避免一次 API 抽风冲掉状态。首次就 CHECK_ERROR 时，status.json 里可以没有这条 key。

status.json 只存每个条目最后一次有效 SAFE / UNSAFE，不存历史。

1. Local

不需要装依赖，标准库即可。先在 GCP 建好 Project、启用 Web Risk API、创建 API Key。

export WEBRISK_API_KEY='…'
export ALERT_WEBHOOK_URL='…'
python3 app/monitor.py

确认 Key 可用（应返回 {"threat":{…}}）：

curl -s "https://webrisk.googleapis.com/v1/uris:search\
?threatTypes=MALWARE\
&uri=http%3A%2F%2Ftestsafebrowsing.appspot.com%2Fs%2Fmalware.html\
&key=$WEBRISK_API_KEY"

服务端调用不带 Referer，API Key 的 Application restrictions 保持 None， 改用 API restrictions 限定只能调 Web Risk。 Zero Trust 证书问题时可临时关掉 TLS 校验，不要当生产默认。

常用环境变量

变量含义
WEBRISK_API_KEYWeb Risk API Key，必填，缺失直接退出
THREAT_TYPES逗号分隔的威胁列表，默认 MALWARE / SOCIAL_ENGINEERING / UNWANTED_SOFTWARE
DOMAINS_FILE域名列表路径
STATE_FILE状态 JSON 路径
LOOKUP_VERIFY_TLS调 Web Risk 时校验 TLS；生产应为 true
ALERT_WEBHOOK_URLTeams / Power Automate 触发器
WEBHOOK_VERIFY_TLSPOST Webhook 时校验 TLS；生产应为 true
FAIL_ON_ERRORtrue 时 CHECK_ERROR / Webhook 失败以非 0 退出；测试 Job 开启，生产默认关
HTTP_TIMEOUT_SECONDSLookup 与 Webhook 共用，默认 15
MAX_RETRIES默认 3
RETRY_DELAY_SECONDS重试间隔，默认 2

2. Docker

基础镜像 python:3.13-slim（约 160 MB），状态挂到宿主机目录。

docker run --rm \
  -v "$PWD/docker-state:/data" \
  -e WEBRISK_API_KEY=… \
  -e ALERT_WEBHOOK_URL=… \
  lifebytehub/portal-monitor:sha-xxxxxxx

开发镜像用 sha-xxxxxxx，生产用 v1.x.x。不要把未验证的 SHA 直接指到 CronJob。

3. Kubernetes

Namespace：portal-monitor。 两个 Secret 都不要进 Git： portal-monitor-webrisk 的 key api-key、 portal-monitor-alert 的 key webhook-url。

配置 ConfigMap + Secret

ConfigMap 挂到 /app/domains.txt；两个 Secret 分别注入 WEBRISK_API_KEY 和 ALERT_WEBHOOK_URL。改域名只 apply ConfigMap。

↓
测试 Job + 测试 PVC

portal-monitor-test 挂 portal-monitor-state-test，不改生产状态。

↓
生产 CronJob + 生产 PVC

portal-monitor 按北京时间每 6 小时跑一次，状态写在 portal-monitor-state 的 /data/status.json。

Test

镜像通常是 CI 的 sha-xxxxxxx。一次性 Job，跑完不占 CPU。状态在测试盘。

Production

镜像用 v1.x.x。Cron 0 */6 * * * + timeZone: Asia/Shanghai，即 00:00 / 06:00 / 12:00 / 18:00。Forbid 禁止重叠。PVC 是 RWO。

  • spec.timeZone 自 K8s 1.27 起为正式特性。低于 1.27 的集群会静默丢弃该字段并继续按 UTC 跑，用 kubectl get cronjob portal-monitor -o jsonpath='{.spec.timeZone}' 确认。
  • gp3 多为 WaitForFirstConsumer：PVC 可能先 Pending，第一个用盘的 Pod 调度后才 Bound。
  • 删 Job / Pod，不要删 PVC，否则下次会当成首次检查，UNSAFE 可能再告一次。
  • 手工立刻跑生产：先 suspend: true，再 kubectl create job --from=cronjob/portal-monitor …。Forbid 不管手工 Job；和生产 Cron 同时跑会抢同一块 RWO。
  • cd-test-job.yml 挂测试 PVC；生产只走 cd-cronjob.yml。不要直接 apply 带 IMAGE_PLACEHOLDER 的 yaml。

4. CI / CD

日常测试跟 main 的 SHA；生产跟 Semver tag。不要把未验证的 sha-… 直接指到 CronJob。

1 · CI push main → 构建镜像

改了 app / Dockerfile / requirements 等会触发 docker-publish.yml，推送 lifebytehub/portal-monitor:sha-<7位>。

↓
2 · 测试 CD 自动或手动跑 Test Job

CI 成功后 cd-test-job.yml 自动跑 SHA 镜像（也可手动填 tag）。 Runner arc-runner-set-portal apply 测试 PVC + ConfigMap，跑 portal-monitor-test 并打日志。

↓
3 · Release 确认无误后打 Git tag

打在已测过的 commit 上，例如 v1.0.1，产出 lifebytehub/portal-monitor:v1.0.1。 这份 tag 镜像不会自动进 Test Job。

↓
4 · 生产 CD 手动更新 CronJob

先用同一 tag 手动跑 cd-test-job.yml，通过后再跑 cd-cronjob.yml 更新生产 CronJob。

  • 改域名：改 k8s/configmap.yaml 再 apply；解析逻辑变了必须发新镜像。
  • CD runner 需要能 kubectl 到 portal-monitor namespace。
  • 上生产前：Actions → CD - Test → image_tag=v1.x.x，过了再跑生产 CD。

怎么确认「没检测出来」是哪一种

先看 Job 日志开头的配置摘要。API key configured: True 说明 Secret 已注入， Found N domain(s) 说明本轮 Pod 已读到 ConfigMap。

  • FATAL: Web Risk rejected the request — Key 无效、被 API restrictions 挡住，或 Web Risk API 没启用。整轮以 2 退出，一个域名都没查。
  • ERROR: WEBRISK_API_KEY not configured — Secret portal-monitor-webrisk 不存在或 key 名不是 api-key。
  • UNSAFE 且 No status change — 检测成功，只是不重复告警。
  • CHECK_ERROR — 超时 / 429 / 5xx，重试耗尽。上次的有效状态会保留。
  • 全部 SAFE 但你确信某页面有问题 — 大概率是 URL 级匹配的问题：清单里写的是裸域名，而被标记的是具体路径。把完整 URL 加进 domains.txt。

可以先用 curl 绕开整个程序，直接确认 Google 那边怎么答：

curl -s "https://webrisk.googleapis.com/v1/uris:search\
?threatTypes=MALWARE\
&threatTypes=SOCIAL_ENGINEERING\
&threatTypes=UNWANTED_SOFTWARE\
&uri=$(python3 -c 'import urllib.parse,sys;print(urllib.parse.quote(sys.argv[1],safe=""))' 'https://例子.com/path')\
&key=$WEBRISK_API_KEY"

返回 {} 就是未命中。这一步能把「程序解析错了」和「Google 本来就没标记」区分开。

Pod 已 Completed 时不能 exec。起一个临时 busybox 挂同一 PVC（RWO：等 monitor 结束再挂）：

ls -l /data
cat /data/status.json

status.json 只有 SAFE / UNSAFE 两种值。 某个域名在里面没有 key，说明它从来没拿到过有效结论（一直 CHECK_ERROR）。

删 Job / Pod，不要删 PVC。状态没了下次会当成首次检查，已经是 UNSAFE 的域名会再告一次。

改判定逻辑必须发新镜像；只改域名清单 apply ConfigMap 就够。
